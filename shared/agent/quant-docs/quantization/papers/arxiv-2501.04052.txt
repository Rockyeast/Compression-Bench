B. Additional Experimental Details
B.1. Details for Baseline Methods
We provide additional details about the baseline quantization methods used in our evaluation.

  • MXFP4: A variant of the microscaling (MX) format, which is standardized by the Open Compute Project (2023).
    A concrete MX-compliant format defines three items: the data format, the block size, and the block scale format.
    By default, the MX block size is 32 with a block scale format of E8M0. The data format can be INT8, FP8-E5M2,
    FP8-E4M3, FP6-E3M2, FP6-E2M3, FP4-E2M1.
  • NVFP4: A custom FP4 format introduced since Blackwell GPU (NVIDIA, 2025b). It applies a fine-grained FP8-E4M3
    scaling factor to each 16-value block, while also leveraging a second-level FP32 scaling factor applied per tensor.
  • NF4: The 4-bit NormalFloat format introduced in QLoRA (Dettmers et al., 2023). It leverages the statistical quantile
    function to derive the 16 quantization values that are information theoretically optimal for normally distributed tensors.
    The 16 quantization values are stored in a high-precision BF16 lookup table. During computation, every quantized
    4-bit element serves as an index to extract the corresponding BF16 value from the lookup table.
  • BlockDialect (Jang & Tambe, 2025): A 4-bit block-wise mixed format that enhances MXFP4. It assigns a per-block
    optimal number format from a formatbook to achieve better data representation. To preserve compatibility with
    energy-efficient low-precision arithmetic, it introduces DialectFP4, a formatbook of FP4 variants that adapt to diverse
    data distributions.
  • GPTQ (Frantar et al., 2023): A weight-only quantization method that uses the second-order Hessian information to
    perform error compensation.
  • AWQ (Lin et al., 2024b): A weight-only quantization method that protects the salient weight channels corresponding to
    larger activation magnitudes. It performs adaptive scaling to scale up the salient weight channels, which can reduce
    their relative quantization error. In addition, it applies weight clipping to further minimize the quantization error.
  • SqueezeLLM (Kim et al., 2024): A weight-only quantization method that (1) Leverage sensitivity-based non-uniform
    quantization to search for the optimal bit precision assignment based on second-order information. (2) Employ
    dense-and-sparse decomposition that stores outlier weights in FP16 using an efficient sparse format.
  • MR-GPTQ (Egiazarian et al., 2026): A weight-activation quantization method that applies Hadamard transformation to
    activations, while using GPTQ to reduce the quantization error of weights.
  • FourOverSix (Cook et al., 2025): A modification to the NVFP4 quantization algorithm that evaluates two potential
    scale factors for each block of values, one by scaling to the full range of FP4 values −6 ∼ 6, and another by scaling to
    a narrower range of −4 ∼ 4. It then selects the optimal scaling based on the mean-squared quantization error.

D. Additional Kernel Evaluation
D.1. Results across Additional Models and Hardware
We extend the evaluation in the main text to additional models from the Qwen and Llama families with different model
sizes and projection shapes, and additionally include results on RTX 5090, which are omitted from the main text for
space. Figure 6 summarizes end-to-end decoding throughput across eight such models over a range of batch sizes. The
observed trends are consistent with the main results: RaZeR achieves near–best-in-class performance at batch size one
and maintains competitive throughput at moderate to large batch sizes, closely tracking Marlin and Marlin-FP4 while
substantially outperforming AWQ and other weight-only quantized kernels. Results on RTX 5090 follow the same scaling
behavior as the server-grade and edge-grade Blackwell GPUs evaluated in the main text, indicating that the performance
characteristics of RaZeR are consistent across different classes of Blackwell devices. Some data points are omitted due to
out-of-memory (OOM) conditions for certain model and batch-size combinations on specific devices.

D.2. Weight-Only Kernel Microbenchmarks
To isolate kernel-level performance from end-to-end model effects, we evaluate weight-only matrix multiplication mi-
crobenchmarks across a broad set of matrix shapes and batch sizes. Tables 16 to 18 report kernel execution time for
representative (M, N, K) configurations corresponding to the linear projections in Llama 3.1 8B and Qwen3-32B on three
GPU platforms.
Across all evaluated configurations, RaZeR achieves performance comparable to or exceeding prior state-of-the-art weight-
only quantization kernels. We report results for both CUDA-core– and tensor-core–based RaZeR implementations, which
exhibit complementary performance regimes depending on batch size. For each configuration, the faster of the two RaZeR
variants is shown in red to indicate the best-performing implementation. Overall, the additional metadata access and
remapping logic introduce minimal kernel-level overhead, with RaZeR consistently matching or outperforming existing FP4
and INT4 kernels across models, layers, batch sizes, and GPUs.

D.3. Tensor-Core Realization of W4A4 RaZeR on Current Hardware
Current NVIDIA tensor cores do not expose a native single-pass datapath for executing RaZeR directly in the W4A4
NVFP4 setting. This appendix therefore evaluates an experimental realization of W4A4 RaZeR on existing GPUs, with
the goal of understanding the attainable compute throughput on current-generation hardware. We focus on large-batch
compute-bound regimes, where weight-only quantization provides limited benefit and can incur additional overhead due to
on-the-fly dequantization on the critical compute path. To this end, we implement a current-hardware realization using
CUTLASS block-scaled NVFP4 GEMM on Blackwell-class GPUs.
This realization decomposes RaZeR into an on-device remapping step followed by two NVFP4 GEMM passes. Due to
current hardware constraints, RaZeR is applied to the weight matrix only, while activations follow the standard block-scaled
NVFP4 tensor-core path.

Two-pass Formulation. RaZeR remaps redundant zeros into signed special values using per-group metadata. Because the
NVFP4 tensor-core datapath expects standard NVFP4 operands, we realize this remapping via a two-pass decomposition of
the weight matrix into two NVFP4 matrices:
                                                  D = ABmain + ABcomp .
The first matrix, Bmain , replaces each redundant +0 with a signed base value, while leaving all nonzero weights unchanged.
The second matrix, Bcomp , provides a small corrective offset so that the sum of the two passes reconstructs the desired
special value. Nonzero entries are masked out in Bcomp .

Example ( {±5, ±8} Configuration). For redundant +0, we set
                                           Bmain : +0 7→ ±4,
                                                         (
                                                           ±1       to select ± 5,
                                           Bcomp : +0 7→
                                                           ±4       to select ± 8,
with the sign and selector determined by 2-bit metadata stored per 16-K group (Sec. 4.2). The two GEMMs are executed
back-to-back and accumulated into the same output buffer.

Generality. This construction applies to any pair of signed special values that can be expressed as the sum of two FP4-
representable values. More generally, for special values s0 = x1 +x2 and s1 = y1 +y2 with FP4-representable x1 , x2 , y1 , y2 ,
Bmain injects the first component while Bcomp injects the second according to the per-group selector bit. All nonzero weights
are preserved in Bmain and masked out in Bcomp . Beyond the values already representable in FP4, this construction
additionally supports the signed special values {±2.5, ±3.5, ±4.5, ±5, ±5.5, ±6.5, ±7, ±7.5, ±8, ±9, ±10, ±12}.

Implementation Details. To avoid host-side unpacking and repacking, we generate Bmain and Bcomp directly on the GPU
in the packed sub-byte layout consumed by CUTLASS. Both passes use block-scaled NVFP4 GEMM with floating-point
accumulation and output, enabling correct two-pass accumulation without introducing additional quantization error.

Performance. Figure 7 reports the throughput of the two-pass W4A4 RaZeR realization across batch sizes and matrix
shapes on RTX 5090. Throughput is reported using an effective operation count of 2M N K multiply-adds, accounting for
both GEMM passes. Across all configurations, throughput increases with batch size and saturates in the compute-bound
regime. In this regime, the two-pass NVFP4 RaZeR realization consistently delivers more than 2× higher throughput over
FP16 GEMM.
Despite these gains, performance remains below that of native single-pass NVFP4 GEMM, reflecting the unavoidable
overhead of executing two separate passes. In particular, the compensation matrix Bcomp is inherently sparse, as it contains
nonzero entries only at locations corresponding to redundant zeros. In our current implementation, this sparsity is not
exploited, and leveraging it within a two-pass realization (e.g., by reducing redundant computation or improving pass
fusion) remains an interesting direction for future work. These observations further motivate the custom RaZeR tensor-core
architecture proposed in Sec. 4.4, which eliminates the need for multi-pass execution altogether.

Figure 8. Optimized partitioning for small weight tensors. The optimized strategy reduces the number of global reduction stages and

In the RaZeR weight-only tensor-core kernel, the weight matrix is partitioned into multiple stripes of approximately equal
length, potentially spanning multiple N -dimensions. Each stripe’s length must be a multiple of 256 to satisfy low-level
kernel design constraints. Each thread block fully occupies one SM, processes one stripe, and accumulates partial results to
global memory.
On modern GPUs with a large number of SMs, this strategy can excessively partition small matrices. We observe that in
the memory-bound scenario, reducing the number of active SMs does not underutilize memory bandwidth. Motivated by
this observation, we introduce an auto-tuning strategy that reduces the number of partitions and global reduction stages to
minimize GEMM and GEMV latency.
Figure 8 illustrates the approach. For a GPU with 10 SMs, the naive strategy utilizes all SMs, resulting in 3–4 reduction
stages per output tile. In contrast, the optimized strategy launches only 8 SMs, reducing the number of global reductions
and improving GEMM/GEMV latency. Table 19 reports profiling results on an NVIDIA RTX 5090 (170 SMs), where the
auto-tuned kernel achieves up to 9.87% throughput improvement.
